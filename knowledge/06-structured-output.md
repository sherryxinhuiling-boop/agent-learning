# 结构化输出与校验重试

## 三层防护

让模型输出可靠数据，需要三层配合，而只有第三层是确定性的：

| 层次 | 手段 | 性质 |
|---|---|---|
| 第一层 | Prompt 写清字段与约束 | 提高概率 |
| 第二层 | API 的 JSON 模式（response_format） | 保证格式合法 |
| 第三层 | 代码校验 + 反馈重试 | 保证内容正确 |

**能用第二层机制保证的事，不要靠第一层求模型听话。** JSON 模式是服务端强制的，比任何 Prompt 措辞都可靠。

## 反馈重试怎么工作

校验失败时，不要重新提问，而是**把具体问题回传给模型**：

```
把上一次的错误输出作为 assistant 消息放进上下文，
再追加一条 user 消息，列出所有不合格的地方，要求重新输出。
```

一次实测的结果：使用较弱的 Prompt 加严格校验，第 1 次输出有 7 项问题（字段名变成中文），第 2 次剩 2 项（情绪字段用了枚举外的值），第 3 次才通过。

**重试次数设 1 到 2 次即可。** 两次都修不对，说明问题出在 Prompt 或任务定义本身，再试十次也不会对。

## 一个反直觉的发现

如果模型**反复试图输出一个你没允许的值**，先别怪它。

实测中模型第二次尝试输出了 `sentiment = "mixed"`，被枚举挡回去了。但那条评价确实又夸又贬 —— **「褒贬都有」是真实存在的类别，缺的是我们的 schema。**

这类信号只有在你认真阅读失败原因时才会发现。它会告诉你：你的数据结构没有覆盖真实世界。

## 失败时必须显式，不要兜底

这是最容易被写错的一处：

```
❌ 校验失败 → 返回默认值 {"rating": 3, ...}
✅ 校验失败 → 返回 {"ok": false, "problems": [...]}
```

兜底版本看起来更「健壮」—— 程序永远不崩、永远有结果。但它把失败这个事实藏了起来。

后果是：一千条数据里混进几十条假数据，你完全看不出来。半年后你会发现报表里 30% 的商品叫「未知」、平均分永远是 3.0，而系统从来没报过一次错。

**让失败出现在统计里、进入人工复核队列，比让它伪装成正常数据安全得多。**

## 一个典型陷阱

Python 里 `isinstance(True, int)` 返回 `True`。所以校验整数字段时，必须先排除布尔值，否则 `True` 会被当成合法的整数 1 通过校验。
