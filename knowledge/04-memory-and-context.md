# 记忆与上下文成本

## 模型本身没有记忆

这是最容易误解的一点。所谓「多轮对话」，是你在每次请求时把**之前所有的消息**重新发一遍。模型只是把整段历史重新读了一次。

理解这一点，才能理解后面的成本问题。

## 三种记忆

**短期记忆** —— 当前对话的消息列表。实现最简单，就是维护一个数组。

**长期记忆** —— 把历史信息存进向量库，需要时检索出来。适合「记住用户三个月前说过的偏好」这类需求。

**工作记忆** —— 当前任务的状态。比如「已经完成了哪几步」「还差什么」。通常用结构化数据保存，而不是塞进对话历史。

## 成本问题的真相

上下文越长，两个问题同时恶化：

第一，**成本上升**。输入 token 是每次都要重新计费的。

第二，**延迟上升**。模型需要处理的内容更多，响应更慢。

一次实测可以看到这个现象：某次对话第二轮，输出只有 5 个 token，但输入涨到了 197 个 token —— 因为整个对话历史被重新发送了一遍。

## 控制上下文的三条策略

**策略一：只保留最近 N 轮。** 最简单，代价是会丢掉久远的信息。

**策略二：压缩历史。** 把早期对话总结成一段摘要，用摘要替换原始消息。保留了信息，但压缩了体积。风险是摘要会丢失细节。

**策略三：按需检索。** 不把所有历史都塞进去，而是把历史存进向量库，每轮只取相关片段。这是长期记忆的做法。

## 选择建议

对话轮数少（10 轮以内），直接用策略一就行。

长对话助手适合策略二，比如每隔 10 轮把前面的内容总结一次。

需要跨会话记住用户信息的场景，才需要策略三。**不要一开始就上向量库**，那是过度设计。
