# RAG 原理与适用场景

RAG 是 Retrieval-Augmented Generation 的缩写，中文通常叫「检索增强生成」。

## 要解决什么问题

大模型有三个先天限制：

**第一，上下文窗口有限。** 你不可能把一本书塞进一次请求。

**第二，会编造。** 对于它不知道的事情，它不会说「不知道」，而是会给出一个听起来很合理的错误答案。

**第三，不知道你的私有数据。** 它没读过你的公司文档、你的笔记、你的代码库。

RAG 的思路很直接：**别让模型记住，让它现查。** 先去你的文档里检索出相关内容，再把这些内容连同问题一起发给模型，让它基于检索结果回答。

## 基本流程

```
文档 → 切块 → 向量化 → 存入向量库
                              ↓
用户提问 → 向量化 → 相似度检索 → 取回相关片段
                              ↓
              问题 + 片段 → 模型 → 带出处的回答
```

索引阶段和查询阶段是分开的。索引可以离线做一次，查询是实时的。

## 什么时候该用 RAG

适合 RAG 的场景：

- 知识会更新，需要随时替换内容（改文档即可，不用重训模型）
- 需要**溯源**，每个答案都要能指回原文出处
- 私有数据，不适合拿去训练
- 数据量大，装不进上下文

**不适合**用 RAG 的场景：

- 所有知识都能放进上下文窗口 —— 那直接全塞进去就行，检索反而多了一层误差
- 任务需要的是推理而不是查找 —— 检索帮不上忙

## RAG 与「长上下文」的关系

上下文窗口越来越大，一个自然的问题是：还需要 RAG 吗？

判断标准是**成本与延迟**，而不只是「装不装得下」。即使窗口装得下 100 万 token，每次请求都为这 100 万 token 付费、并等待它被处理，这在多数产品里都不可接受。

所以结论是：**知识量大、调用频繁 → 用 RAG；数据小、调用少 → 直接塞进上下文。**

## 最常见的失败点

RAG 出问题的地方，八成不在「生成」，而在「检索」。

模型很擅长基于给定材料回答，但它没办法回答一个**根本没被检索出来**的片段。检索没召回到正确内容，后面的生成再强也没用。

**所以优化 RAG 的顺序永远是：先保证召回，再优化生成。**
