# 评测与可观测性

## 为什么必须有测试集

没有测试集时，你改 Prompt、换模型、调切块大小，**完全无法判断是变好了还是变坏了**。

凭感觉优化的结果是：今天觉得好一点，明天觉得差一点，一个月后你手上有一堆改动，但说不出哪一条真正起了作用。

测试集的作用是把「感觉」变成「数字」。

## 测试集怎么建

**规模**：20 到 50 题就足够起步。不要一开始追求上百题，那会让你迟迟不开始。

**格式**：每题至少记录三样东西 —— 问题、标准答案、答案出处（在哪份文档的哪一段）。

**题型必须多样**，这是最关键的一点：

| 题型 | 作用 |
|---|---|
| 单文档事实题 | 检查基本检索能力 |
| 跨文档综合题 | 检查能否把多个来源的信息合起来 |
| 易混淆题 | 语料里有两个相似概念，检查能否区分 |
| 数值/条件题 | 检查精确信息的召回 |
| **无法回答题** | **最重要的一类** |

## 无法回答题为什么最重要

这类题目的正确答案是「**文档里没有提到**」。

它检测的是：系统会不会在检索不到内容时**硬编一个答案**。

RAG 系统最危险的失败模式不是答错，而是**自信地答错** —— 用户看不出区别，会直接采信。如果测试集里全是能回答的题，这个缺陷永远不会暴露。

**一个没有「无法回答题」的测试集，是不合格的。**

## 评测要分两层

不管评测的是抽取任务还是 RAG，判定都必须分两层：

- **格式层**：答案结构是否正确（能否解析、字段是否齐全）
- **内容层**：答案内容是否正确（事实是否准确、出处是否真的支持这个结论）

只测一层会漏掉大量问题。

## 必须能区分假阴性与假阳性

- **假阴性**：系统做对了，被评测标准错误地判为失败
- **假阳性**：系统做错了（比如编造），但结构合法所以被判为通过

**只报告一个「通过率」是没有信息量的。** 你必须能回答：失败里有多少是被冤枉的？通过里有多少是蒙对的？

这两类错误的成因往往同源 —— 比如 Prompt 说「可以留空」，而校验代码不接受空值，就会同时制造出假阴性（对的被拒）和假阳性（模型为了填满而编造）。

## 可观测性

上线之后，你需要知道每一次调用发生了什么：

- 完整链路：问题 → 检索到哪些块 → 送给模型的提示 → 模型输出
- token 与成本：哪一步最贵
- 错误率与延迟分布
- 用户反馈

**没有可观测性的 AI 系统等于黑箱。** 用户说「它答错了」，你连当时检索到什么都没法复现，就只能靠猜。

## 三个必须能报出来的数字

任何一个 AI 产品上线前，你都应该能准确说出：

1. 任务准确率（用测试集跑出来的）
2. 平均响应时间
3. 单次调用成本

说不出这三个数字，就还算不上「知道这个系统表现如何」。
