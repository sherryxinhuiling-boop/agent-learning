# Prompt 工程要点

## 结构化输出的最小可用集合

要让模型稳定返回可被程序解析的结构化数据，Prompt 里必须包含四样东西：

1. **角色** —— 它是谁（一句话即可）
2. **字段定义** —— 有哪些字段、每个字段是什么含义
3. **类型约束** —— 每个字段的数据类型
4. **输出约束** —— 只输出 JSON 本身，不要解释文字，不要用代码块包裹

缺了第 3 项，模型可能把布尔值写成字符串；缺了第 4 项，输出会被 markdown 代码块包住，导致解析失败。

## 两层判定：格式与内容

评测模型输出必须分两层：

- **格式层**：能否被 `json.loads()` 解析
- **内容层**：字段名、类型、取值范围是否正确

只测格式层会漏掉大量问题。一个真实案例：「提取这段评价的信息，用 JSON 格式输出」这个 Prompt 产出了完全合法的 JSON，但字段名全变成了中文、布尔值变成了字符串、还多出几个未定义的字段。

**格式可解析不等于内容可用。** 只测第一层的脚本会判它通过，而下游代码一读就崩。

## few-shot 示例的隐藏副作用

加一个输入输出示例能显著提升稳定性，尤其是输出格式比较特殊的时候。但示例有一个容易被忽略的副作用：

**模型会模仿示例的「形状」，包括字段的完整度。**

如果示例里每个字段都有值，模型在原文依据不足时也会倾向于把字段填满 —— 也就是**编造**。要避免这一点，示例里必须专门留一个「原文没有提到的信息填 null」的样例。

## 事实类约束与判断类约束

写字段定义时要区分两类：

**事实类**（如商品名、评分、是否推荐）—— 必须来自原文。要明确写：原文没有明确提到时填 null，绝对不要根据语气推测。

**判断类**（如优缺点列表、情绪倾向）—— 本身就是分析结论，允许模型推断。

如果不做这个区分，模型会把「推测」和「陈述」混在一起输出，而下游完全无法分辨哪个数字是用户说的、哪个是模型猜的。

## 温度参数

结构化输出任务建议用 `temperature=0`。这个参数越低，输出越稳定、越接近确定性的结果；越高越有创造性，也越容易跑偏。

需要创意写作时才调高它。
